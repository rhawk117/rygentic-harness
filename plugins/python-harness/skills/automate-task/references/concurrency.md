## Verified defaults and facts

- `ThreadPoolExecutor(max_workers=None)` defaults to `min(32, (os.process_cpu_count() or 1) + 4)` in Python 3.13+. The limit preserves at least some I/O concurrency while capping implicit resource use. \[doc-verified: https://docs.python.org/3.14/library/concurrent.futures.html#concurrent.futures.ThreadPoolExecutor]
- `ProcessPoolExecutor(max_workers=None)` defaults to `os.process_cpu_count()`. On Windows, `max_workers` must be at most 61. \[doc-verified: https://docs.python.org/3.14/library/concurrent.futures.html#concurrent.futures.ProcessPoolExecutor]
- `ProcessPoolExecutor(max_tasks_per_child=...)` was added in Python 3.11 and replaces a worker after the configured number of tasks; the default is `None`. \[doc-verified: https://docs.python.org/3.14/library/concurrent.futures.html#concurrent.futures.ProcessPoolExecutor]
- `Executor.shutdown(cancel_futures=True)` was added in Python 3.9 and cancels pending futures that have not started; running futures continue. \[doc-verified: https://docs.python.org/3.14/library/concurrent.futures.html#concurrent.futures.Executor.shutdown]
- `InterpreterPoolExecutor` gives each worker its own interpreter and GIL. Mutable objects are not shared between interpreters; callables, arguments, initializers, and results are serialized with `pickle`, so only picklable values can cross the boundary. \[doc-verified: https://docs.python.org/3.14/library/concurrent.futures.html#concurrent.futures.InterpreterPoolExecutor]
- On POSIX systems other than macOS, Python 3.14 changes the multiprocessing default start method from `fork` to `forkserver`. \[doc-verified: https://docs.python.org/3.14/whatsnew/3.14.html#multiprocessing]
- Free-threaded CPython is officially supported but remains optional in Python 3.14. Its single-threaded performance penalty is roughly 5–10%, depending on platform and compiler. \[doc-verified: https://docs.python.org/3.14/whatsnew/3.14.html#free-threaded-cpython]
- `os.cpu_count()` reports logical CPUs available to the system, while `os.process_cpu_count()` reports CPUs available to the calling process and may reflect CPU affinity. \[doc-verified: https://docs.python.org/3.14/library/os.html#os.cpu_count]
- `os.sched_getaffinity(0)` can expose the process CPU affinity set on supported platforms. \[doc-verified: https://docs.python.org/3.14/library/os.html#os.sched_getaffinity]
- Python 3.13+ supports overriding CPU-count results with `PYTHON_CPU_COUNT` or `-X cpu_count`. \[doc-verified: https://docs.python.org/3.14/library/os.html#os.cpu_count]
- A free-threaded build can be identified with a `python3.14t` executable where provided, `sys._is_gil_enabled()`, or `sysconfig.get_config_var("Py_GIL_DISABLED")`. \[doc-verified: https://docs.python.org/3.14/howto/free-threading-python.html#identifying-free-threaded-python]
- `PYTHON_GIL` can control whether the GIL is enabled where supported. Importing an incompatible C-extension module can automatically re-enable the GIL. \[doc-verified: https://docs.python.org/3.14/howto/free-threading-python.html#the-gil]
- In Python 3.12+, using the `fork` multiprocessing start method when Python detects multiple threads emits a `DeprecationWarning`; use `forkserver` or `spawn` where appropriate. \[doc-verified: https://docs.python.org/3.14/library/multiprocessing.html#contexts-and-start-methods]
- `resource.RLIMIT_NOFILE` is the maximum number of open file descriptors for the current process, so large connection or subprocess fan-out must stay below the effective limit. \[doc-verified: https://docs.python.org/3.14/library/resource.html#resource.RLIMIT_NOFILE]
- `asyncio.TaskGroup` was added in Python 3.11 and cancels sibling tasks when a member task fails; `asyncio.timeout()` was also added in Python 3.11 and converts deadline cancellation into `TimeoutError` outside the context manager. \[doc-verified: https://docs.python.org/3.14/library/asyncio-task.html#task-groups]
- `asyncio.to_thread()` runs a blocking callable in a separate thread, but due to the GIL it is generally intended for blocking I/O rather than CPU-bound Python code. \[doc-verified: https://docs.python.org/3.14/library/asyncio-task.html#asyncio.to_thread]
- Python documentation does not promise that `os.cpu_count()` or `os.process_cpu_count()` interprets cgroup CPU quotas in every deployment. Treat cgroup-quota handling as environment-dependent and verify it at runtime when container limits matter. [stdlib: confirm via search_python_docs "os.process_cpu_count"]
- A practical runtime cap can combine `os.process_cpu_count()`, `os.sched_getaffinity(0)` where available, cgroup quota information, file-descriptor limits, remote rate limits, and memory per worker. The exact formula is application-specific.

## Classifying the workload

- **I/O-bound:** Waiting on HTTP APIs, DNS, databases, object storage, files, or sockets. Prefer `asyncio` for async-capable clients; use `ThreadPoolExecutor` or `asyncio.to_thread()` for blocking clients.
- **CPU-bound:** Parsing, compression, cryptography, image processing, or numerical work that consumes CPU. Prefer vectorized/native library execution, `ProcessPoolExecutor`, or `InterpreterPoolExecutor` when task size justifies serialization and startup costs.
- **Subprocess-bound:** Running CLIs, compilers, media tools, or shell commands. Prefer `asyncio.create_subprocess_exec()` for many concurrent subprocesses with explicit timeouts and a semaphore; use synchronous `subprocess.run()` for simple sequential work.
- **Library-parallel:** Work already parallelized inside DuckDB, Polars, NumPy, BLAS, or OpenMP. Prefer one library-level pool and cap its workers; do not automatically wrap it in another executor.

## multiprocessing

Use this section when the user names `multiprocessing`, processes, or "use all cores", or when the workload is CPU-bound pure Python over independent inputs. An explicit choice is preserved; see `parallelism-and-overrides.md`.

- **Default generation:** `concurrent.futures.ProcessPoolExecutor(max_workers=N, mp_context=multiprocessing.get_context(...))` with `executor.map(fn, items, chunksize=K)` or `submit()` plus `as_completed()`. It gives per-task exceptions, `shutdown(cancel_futures=True)`, and the same shape as the thread version. \[doc-verified: https://docs.python.org/3.14/library/concurrent.futures.html]
- **When the user literally says "use multiprocessing":** generate `multiprocessing.get_context(method).Pool(processes=N, maxtasksperchild=M)` inside a `with` block and iterate `pool.imap_unordered(fn, items, chunksize=K)`. Without the context manager, or `close()` plus `join()`, the process can hang on finalization. \[doc-verified: https://docs.python.org/3.14/library/multiprocessing.html#multiprocessing.pool.Pool]
- **Start methods:** In 3.14, POSIX defaults to `forkserver` and macOS and Windows default to `spawn`. `fork` is no longer the default anywhere, and code that needs it must request it through `get_context('fork')`. Generated scripts call `get_context()` explicitly so behavior does not depend on the platform. Prefer `forkserver` on Linux and `spawn` elsewhere. \[doc-verified: https://docs.python.org/3.14/library/multiprocessing.html#contexts-and-start-methods]
- **Main guard and pickling:** Under `spawn` and `forkserver`, the main module is re-imported, so all pool creation stays under `if __name__ == '__main__':`. Worker functions and their arguments must be picklable: use top-level functions, `functools.partial` over top-level functions, and frozen dataclasses. Lambdas, nested functions, open handles, and live clients will not pickle. \[doc-verified: https://docs.python.org/3.14/library/multiprocessing.html#the-spawn-and-forkserver-start-methods]
- **chunksize:** Both `Pool.imap_unordered` and `Executor.map` default to `chunksize=1`. For many small tasks, set `chunksize = max(1, len(items) // (workers * 4))`. Very long iterables benefit most. \[doc-verified: https://docs.python.org/3.14/library/multiprocessing.html#multiprocessing.pool.Pool.imap]
- **Worker recycling:** `max_tasks_per_child` (executor) or `maxtasksperchild` (Pool) replaces leaking workers. On `ProcessPoolExecutor` it selects `spawn` unless you pass `mp_context`, and it cannot be combined with `fork`. Require 3.14.7 or later when using it, because that release fixes a hang that occurred when queued tasks remained after a worker retired. \[doc-verified: https://docs.python.org/3.14/library/concurrent.futures.html#processpoolexecutor]
- **Sharing data:** Pass small inputs as arguments and return small results. For large read-only arrays, use `multiprocessing.shared_memory.SharedMemory`: the creator calls `unlink()` exactly once, and every process calls `close()`. `Queue` and `Manager` proxies pickle each item and round-trip through a server process, so use them only for coordination, never for bulk data. \[doc-verified: https://docs.python.org/3.14/library/multiprocessing.shared_memory.html]
- **Worker count:** Default to `os.process_cpu_count()` (respects affinity and `PYTHON_CPU_COUNT`). On Windows, the executor rejects `max_workers` above 61. Cap by memory per task as well as by cores. \[doc-verified: https://docs.python.org/3.14/library/concurrent.futures.html#processpoolexecutor]

## Pitfalls

- **Oversubscription:** Do not multiply outer workers by inner BLAS/OpenMP/library workers; set one deliberate concurrency budget.
- **Unbounded `gather()`:** Creating one task per input can exhaust memory, sockets, or rate limits; use a semaphore, bounded queue, or producer limit.
- **Threads for CPU-bound Python under the GIL:** Threads usually do not provide parallel execution for pure Python CPU work; use processes, subinterpreters, native code, or a free-threaded build with compatible extensions. \[doc-verified: https://docs.python.org/3.14/library/asyncio-task.html#asyncio.to_thread]
- **Processes for tiny tasks:** Serialization and process startup can exceed useful work; batch tasks or stay sequential/threaded when tasks are small.
- **Unpicklable callables:** Process and interpreter pools require picklable callables and arguments; avoid lambdas, nested functions, open handles, and live client objects at the pool boundary. \[doc-verified: https://docs.python.org/3.14/library/concurrent.futures.html#concurrent.futures.ProcessPoolExecutor]
- **Missing timeouts:** Every network request, subprocess, and pool wait should have a deadline appropriate to the operation.
- **Ignoring cancellation:** Preserve `CancelledError` and terminate or reap subprocesses; cancellation of a future does not stop already-running work. \[doc-verified: https://docs.python.org/3.14/library/concurrent.futures.html#concurrent.futures.Executor.shutdown]
- **Assuming Ctrl-C is cleanup:** Arrange explicit signal handling, executor shutdown, subprocess termination, and temporary-resource cleanup.
- **Forking after threads start:** Avoid relying on `fork` in multithreaded programs; Python 3.12+ warns when it detects this pattern. \[doc-verified: https://docs.python.org/3.14/library/multiprocessing.html#contexts-and-start-methods]
- **Ignoring file-descriptor limits:** Connection and subprocess fan-out can hit `RLIMIT_NOFILE` before CPU becomes the bottleneck. \[doc-verified: https://docs.python.org/3.14/library/resource.html#resource.RLIMIT_NOFILE]
