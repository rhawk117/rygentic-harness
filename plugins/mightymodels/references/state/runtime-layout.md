# Runtime layout for hooks

Read before changing a hook. A hook is a CLI subcommand of `mightymodels` that `hooks/hooks.json` runs, and it works from the state database below and from git. It never defines a second state model, and it keeps no file of its own to remember what it did.

## Where the state database is

The state database is `mightymodels.db` in the plugin data directory, the directory Claude Code names in `CLAUDE_PLUGIN_DATA` for the state server and for hook commands. It is outside every repository and serves all of them: each row carries a repository key, the origin remote's `owner/name` or, with no origin, a hash of the toplevel path. An origin that is not exactly `owner/name` on a host gets the path hash too: a subgroup path such as `group/sub/name`, a path of one name, a local path or a `file://` URL. Checkouts keyed by their path each keep their own rows, and one that moves starts empty. A command run through the Bash tool gets none of the plugin's variables, so the SessionStart hook, `mightymodels session-start`, appends one line to the session's env file (`CLAUDE_ENV_FILE`) that exports the same directory as `MIGHTYMODELS_DATA_DIR`, and `mightymodels verify run` reads that to open the file the server opened. Without the variable, or outside a git work tree, the server answers every tool call with what is missing and `verify run` exits 2 with the same on standard error.

Every session of every repository writes that one file. It is kept in SQLite's write-ahead log mode, so `mightymodels.db-wal` and `mightymodels.db-shm` sit beside it while a session has it open, and every connection has a busy timeout of 10 seconds: a write waits that long for another session's write before it is refused as locked. The mode is set only after the schema version stamp is accepted.

This breaks with earlier versions, which kept the database inside the repository under `.mightymodels/`. That file is not read, imported or changed, so state recorded in it does not carry over, and it can be deleted. The new file carries a schema version stamp, and a file with another stamp is refused by name instead of read, and nothing is written to it. One column was added under the same stamp, `auto_escalate` on `tickets`: it has a default of off, and a file whose `tickets` table was made before it gets the column added the next time it is opened, so its tickets keep working and read as off.

## The hooks

Under GitHub Copilot the plugin ran five hooks. Each has a counterpart now. Each of those hook commands exits 0 whatever happens and says on standard error why it did nothing (no data directory, not a git work tree, a database it refuses); only the completion gate ever answers a block, and only as below. The three that can stop something go through `bin/mightymodels-hook`, a `sh` wrapper that turns any failure of the Python process into exit 0 with one line on standard error, because exit 2 from a `SubagentStop` or `PreCompact` hook blocks.

| session bootstrap   | `SessionStart`                                                | `session-start` (`bin/mightymodels`)              | `CLAUDE_PLUGIN_DATA`, `CLAUDE_ENV_FILE`, the env file                                                                      | one `export MIGHTYMODELS_DATA_DIR=...` line to the env file, unless it is already there                                                                 |
| decision recorder   | none: elicitation persistence (T11) replaces it                | none                                              | not applicable                                                                                                             | not applicable                                         |
| subagent recorder   | `SubagentStop` (`^mightymodels:triage:(code-scout\|web-scout)$`) and `PostToolUse` (`SubagentHandback`) | `subagent-record` and `subagent-handback` (`bin/mightymodels-hook`) | the hook input (`agent_type`, `agent_id`, and `last_assistant_message` on the stop or `tool_input.message` on the hand-back), the data directory, git for the repository key | one file in `scout-spool/` in the data directory, named `spool_file_prefix(key)`, `stop-` or `handback-`, a unique part and `.json`, written as `.part` and renamed |
| completion gate     | `SubagentStop` (`^mightymodels:workers:(engineer\|architect\|intern)$`) | `completion-gate` (`bin/mightymodels-hook`)       | the hook input (`agent_type`, `stop_hook_active`), the ticket on the checked-out branch, its in-progress tasks, the briefs | on standard output `{"decision": "block", "reason": ...}` when a task the worker started has no brief DONE half naming a commit; no file, no row        |

The plugin also has two `PreToolUse` hooks with no Copilot counterpart: `dispatch-hook` (`bin/mightymodels-dispatch-hook`) on `Agent`, and `main-thread-hook` (`bin/mightymodels-main-thread-hook`) on `Edit`, `Write` and `Bash`. They are the two hooks that refuse, and "The dispatch hook" and "The main-thread hook" below have their rules.

Every entry in `hooks/hooks.json` has a `timeout` of 10 seconds. Claude Code cancels a hook at its timeout and goes on as if the hook had answered nothing: the recorder keeps no report, the completion gate does not hold the stop, the snapshot is not written, and a dispatch, an edit or a push is not checked. The dispatch wrapper and the main-thread wrapper therefore stop their own commands after 8 seconds and answer for them, as below.

### The dispatch hook

A caller whose `agent_type` begins `mightymodels:` is a plugin worker. Any other caller is judged as the main thread: no `agent_type`, one that is not a string, a built-in subagent, another plugin's agent. A target is a worker under its type or its bare name.

| Caller        | Target                       | State                                                                                              | Answer                                         |
| ------------- | ---------------------------- | -------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| plugin worker | outside its agent file's row | not read                                                                                           | deny, naming the row                           |
| anyone        | intern                       | the intern has no task in progress, or one owning other than one file, or the state cannot be read | deny, naming the engineer                      |
| main thread   | engineer or architect        | no ticket directory, or no unclosed ticket on the branch                                           | no decision                                    |
| main thread   | engineer or architect        | one unclosed ticket on the branch with no task in progress                                         | deny, naming the `task` tool's `start`         |
| main thread   | engineer or architect        | several unclosed tickets on the branch                                                             | no decision, and a `systemMessage` naming them |
| main thread   | engineer or architect        | the state cannot be read                                                                           | deny until it can                              |
| main thread   | architect or wingman         | one unclosed ticket on the branch with a task a block stopped, and its `auto-escalate` off         | `ask`, naming each such task and its reasons   |
| main thread   | wingman                      | anything else, the state that cannot be read included                                              | no decision                                    |
| main thread   | any other type               | not read                                                                                           | no decision                                    |

A ticket directory is a directory under `.mightymodels/` other than `archives`, at the project directory or above it. A repository without one has no ticket, so the hook opens no database there and runs no git command.

The `ask` row puts a block to the user before an escalation is spent on it. A block stopped a task that is `blocked` or `failed`, and one that is in progress on an attempt of the architect's that started from `blocked` or `failed`: agents-assemble marks the task and starts it for the architect before it dispatches, so by then the task reads in progress. The reasons shown are those of the task's latest move into `blocked` or `failed`. A task the architect started from any other status, a `diagnose-replan` from review for one, has no block behind it. For the architect the rows above it are judged first, so a blocked task that was not started again is denied, not asked about. `auto-escalate` is the key under `handoff-context` in ticket.yml as `ticket` `validate` last stored it, off when the key is absent; with it on the row gives no decision.

The wrapper answers when its command fails, is killed or runs past 8 seconds (`MIGHTYMODELS_DISPATCH_SECONDS` sets another limit). It exits 2, which refuses the dispatch, for a plugin worker, and for any other caller whose target is the engineer, the architect or the intern when `.mightymodels` exists at the project directory (`CLAUDE_PROJECT_DIR`, or else the working directory). Every other dispatch goes ahead with one line on standard error saying it was not checked, a dispatch of the wingman that the command would have answered `ask` among them. The command's own standard error is passed through.

### The main-thread hook

While the checked-out branch has one unclosed ticket, the main thread hands repository edits to a worker and pushes only a proven landing. The caller rule is the dispatch hook's. A plugin worker's `Edit`, `Write` and `Bash` get no decision. `git commit` is not judged.

| Caller        | Tool              | Input                                                 | State                                                    | Answer                                               |
| ------------- | ----------------- | ----------------------------------------------------- | -------------------------------------------------------- | ---------------------------------------------------- |
| plugin worker | any               | any                                                   | not read                                                 | no decision                                          |
| main thread   | `Edit` or `Write` | a path in a ticket directory                          | not read                                                 | no decision                                          |
| main thread   | `Edit` or `Write` | any other path                                        | one unclosed ticket on the branch                        | `ask`, naming the ticket and the path                |
| main thread   | `Edit` or `Write` | any other path                                        | the state cannot be read                                 | no decision, and a `systemMessage` saying so         |
| main thread   | `Bash`            | a command that names no push                          | not read                                                 | no decision                                          |
| main thread   | `Bash`            | a command that names a push                           | one unclosed ticket on the branch, not ready to land     | deny, naming what is open and `stick-the-landing`    |
| main thread   | `Bash`            | a command that names a push                           | one unclosed ticket on the branch, ready to land         | no decision                                          |
| main thread   | `Bash`            | a command that names a push                           | the state cannot be read                                 | deny until it can                                    |
| main thread   | any of the three  | an edit outside the ticket directories, or a push     | no ticket directory, or no unclosed ticket on the branch | no decision                                          |
| main thread   | any of the three  | an edit outside the ticket directories, or a push     | several unclosed tickets on the branch                   | no decision, and a `systemMessage` naming them       |

A path is in a ticket directory when, once resolved, it lies below a directory under `.mightymodels/` other than `archives`, at the project directory or above it, whether or not it exists yet. A relative path counts from the working directory of the hook, and `..` or a symbolic link that leads out of the directory leads out of the answer too.

A ticket is ready to land when the `task` tool's `ready` action would give no reason, read through the functions `ready` reads them through (no plan task pending, in progress, failed or blocked, and every live contract command passing at HEAD), and each of those passing receipts was taken in the landing phase, which is what `mightymodels verify run --slug SLUG --all --phase landing` writes. A commit made after the proof moves HEAD, so a push is held again until the contract is proven at the new HEAD. The hook writes nothing.

A push is found in the command's shell words, never in its text: a word that is `git`, bare or under a path, followed by git's own options (`-C DIR`, `-c NAME=VALUE`, `--git-dir`, `--work-tree` and the like) and then the word `push`. It is found wherever it stands: after `&&`, `;`, `|` or a newline, inside `( )`, `$( )` or backticks, behind an assignment, a keyword or a wrapper such as `sudo`, `env` or `xargs`, in the command given to `sh`, `bash`, `zsh`, `dash` or `ksh` with `-c`, in the words of an `eval`, and in a quoted word that holds a command substitution and no here-document. So `echo "git push"`, `git pushd`, `git stash push` and a commit message that says `git push` are no push. Where the hook cannot place the words it answers as for a push: a command that cannot be split into words because a quote never closes and that has the words `git` and `push`, the bare words `git push` of another command (`echo git push`, a line of an unquoted here-document), a variable where git's options go (`git $FLAGS push`), and hook input that is not the expected JSON but names the `Bash` tool and has both words. A push the words do not show is not held: a git alias, `git subtree push`, `git lfs push`, `git send-pack`, a variable that holds `git` or `push`, a script, a string given to `ssh`, and `gh pr create`.

The wrapper answers when its command fails, is killed or runs past 8 seconds (`MIGHTYMODELS_MAIN_THREAD_SECONDS` sets another limit). A plugin worker's call, and any call where `.mightymodels` does not exist at the project directory (`CLAUDE_PROJECT_DIR`, or else the working directory), goes ahead in silence. Otherwise an `Edit` or `Write` goes ahead with a `systemMessage` saying it was not checked, a `Bash` call exits 2, which refuses it, when the text after its `"command":"` has `git` and later `push`, and every other call goes ahead in silence. The command's own standard error is passed through.

### The branch ticket

A hook's ticket is the one ticket of the repository, not closed, whose `branch` is the checked-out branch. A detached HEAD, no match, or two matches mean no ticket: the completion gate and the snapshot do nothing.

### The completion gate

When `mightymodels:workers:engineer`, `mightymodels:workers:architect` or `mightymodels:workers:intern` stops, the gate looks for in-progress tasks whose latest attempt was that worker's. A plan task (`T` id) whose brief `.mightymodels/SLUG/briefs/task-NN.md` is missing, or has no `## DONE` half with a `commit: <hash>` line, blocks the stop; the reason names the task and what is missing. A `C` or `R` task has no brief and is not held. The gate keeps no marker of its own: Claude Code sets `stop_hook_active` on the stop that follows a block, and the gate lets that stop through, so a worker that cannot finish is never trapped. A worker with nothing in progress, any other agent type and a stop with no ticket pass untouched.

### The subagent recorder

On Claude Code 2.1.271 or later in auto mode a scout delivers its report through the `SubagentHandback` tool, and the `last_assistant_message` of its `SubagentStop` is closing text. The `PostToolUse` hook on `SubagentHandback` spools the call's `tool_input.message` (the input carries the scout's `agent_type` and `agent_id`); the `SubagentStop` hook spools `last_assistant_message`, which is the report of a session with no hand-back. Both targets are the scout and the `agent_id`, since the input carries no dispatch. Neither hook ever blocks or changes a hand-back. The recorder opens no database: the state server takes the file in on its next tool call, takes in a `handback-` file before any `stop-` file, and drops a `stop-` file when a report of that scout and target is stored, so one report is kept per agent and the handed-back one wins. A report whose file would pass the spool's cap (`SPOOL_FILE_BYTES`, sized from `REPORT_LIMIT`) is not written; one over `REPORT_LIMIT` characters is written and set aside by the server. `docs/state.md` has the spool's name and format.

### Snapshot files

The pre-compact hook writes the two files the `snapshot` tool describes under the ticket's `handoffs/`, limit 20 per list. `.mightymodels/` is excluded from git by the same call that opens the database, before anything is written there.
